# 接收代码评审（Code Review Reception）

## 概述

代码评审需要技术评估，而非情绪表演。

**核心原则：** 先验证再实施。先询问再假设。技术正确性优先于社交舒适。

## 响应模式

```
WHEN receiving code review feedback:

1. READ（阅读）: 完整阅读反馈，不做出反应
2. UNDERSTAND（理解）: 用自己的话复述需求（或询问）
3. VERIFY（验证）: 对照代码库实际情况检查
4. EVALUATE（评估）: 对该代码库而言，技术上是否合理？
5. RESPOND（响应）: 技术确认或有理有据的反驳
6. IMPLEMENT（实施）: 一次一项，每项都测试
```

## 禁止的回应

**绝不（NEVER）：**
- "你说的完全正确！"（违反 CLAUDE.md 规定）
- "好主意！" / "非常好的反馈！"（表演性）
- "我现在就来实施"（在验证之前）

**应该（INSTEAD）：**
- 复述技术要求
- 提出澄清问题
- 如果错误，用技术推理反驳
- 直接开始工作（行动胜于言辞）

## 处理不明确的反馈

```
IF any item is unclear:
  STOP - 暂不实施任何内容
  ASK - 就不明确的条目请求澄清

WHY: 各条目可能相互关联。部分理解 = 错误实施。
```

**示例：**
```
你的人类伙伴 (your human partner): "修复 1-6"
你理解了 1,2,3,6。对 4,5 不清楚。

❌ 错误: 现在实施 1,2,3,6，稍后再问 4,5
✅ 正确: "我理解了 1,2,3,6 条。在继续之前，需要澄清 4 和 5。"
```

## 按来源分类处理

### 来自你的人类伙伴
- **可信** —— 理解后实施
- **仍要询问** —— 如果范围不明确
- **不做表演性同意**
- **直接行动**或技术确认

### 来自外部评审者
```
BEFORE implementing:
  1. 检查: 对这个代码库技术上是否正确？
  2. 检查: 是否破坏现有功能？
  3. 检查: 当前实现的理由是什么？
  4. 检查: 是否在所有平台/版本上都能工作？
  5. 检查: 评审者是否理解完整上下文？

IF suggestion seems wrong:
  用技术推理反驳

IF can't easily verify:
  说明: "没有 [X] 我无法验证这个。我应该 [调查/询问/继续]？"

IF conflicts with your human partner's prior decisions:
  立即停止并与你的人类伙伴讨论
```

**你的人类伙伴的规则：** "外部反馈——保持怀疑，但要仔细检查"

## 「专业」功能的 YAGNI 检查

```
IF reviewer suggests "implementing properly":
  在代码库中 grep 实际使用情况

  IF unused: "这个端点没有被调用。移除它（YAGNI）？"
  IF used: Then implement properly
```

**你的人类伙伴的规则：** "你和评审者都向我汇报。如果我们不需要这个功能，就不要添加。"

## 实施顺序

```
FOR multi-item feedback:
  1. 首先澄清不明确的部分
  2. 然后按以下顺序实施:
     - 阻塞性问题（故障、安全问题）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项单独测试
  4. 验证无回归
```

## 何时反驳

在以下情况下反驳：
- 建议破坏现有功能
- 评审者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对该技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的人类伙伴的架构决策冲突

**如何反驳：**
- 使用技术推理，而非防御性态度
- 提出具体问题
- 引用通过测试的代码
- 如果是架构性问题，让你的人类伙伴参与

**如果不便公开反驳时的信号:** "Strange things are afoot at the Circle K"

## 确认正确的反馈

当反馈确实是正确的：
```
✅ "已修复。[简要描述更改内容]"
✅ "Good catch - [具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你说的完全正确！"
❌ "好主意！"
❌ "感谢发现这个问题！"
❌ "感谢 [任何内容]"
❌ 任何感恩的表达
```

**为什么不感谢：** 行动说明一切。直接修复就好。代码本身表明你听到了反馈。

**如果你发现正要写"谢谢"：** 删掉它。改为说明修复了什么。

## 优雅地纠正自己的反驳

如果你反驳了但发现自己错了：
```
✅ "你是对的——我检查了 [X]，它确实 [Y]。现在实施。"
✅ "验证过了，你是对的。我最初的理解有误，因为 [原因]。正在修复。"

❌ 长篇道歉
❌ 为自己反驳辩护
❌ 过度解释
```

实事求是地说明纠正并继续。

## 常见错误

| 错误 | 正确做法 |
|---------|-----|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量实施不测试 | 一次一项，每项都测试 |
| 假设评审者是对的 | 检查是否破坏现有功能 |
| 避免反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有条目 |
| 无法验证，仍然继续 | 说明限制，请求指导 |

## 真实示例

**表演性同意（错误）：**
```
评审者: "移除遗留代码"
❌ "你说的完全正确！让我移除那个……"
```

**技术验证（正确）：**
```
评审者: "移除遗留代码"
✅ "正在检查……构建目标是 10.15+，这个 API 需要 13+。需要保留遗留代码以保持向后兼容。当前实现有错误的 bundle ID——修复它还是放弃 13 之前版本的支持？"
```

**YAGNI（正确）：**
```
评审者: "实现适当的指标追踪，包括数据库、日期过滤、CSV 导出"
✅ "已 grep 代码库——没有任何地方调用这个端点。移除它（YAGNI）？还是我遗漏了什么使用场景？"
```

**不明确条目（正确）：**
```
你的人类伙伴 (your human partner): "修复 1-6 条"
你理解了 1,2,3,6。对 4,5 不清楚。
✅ "理解了 1,2,3,6。在实施之前需要澄清 4 和 5。"
```

## GitHub 讨论串回复

在 GitHub 上回复内联评审评论时，在评论讨论串中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，而非必须遵循的命令。**

验证。质疑。然后实施。

不做表演性同意。始终保持技术严谨。
