# 系统性调试 (Systematic Debugging)

## 概述

随机碰运气的修复浪费时间并创造新 bug。快速补丁掩盖了根本问题。

**核心原则：** 在尝试修复之前，始终 (ALWAYS) 找到根因。修复症状就是失败。

**违反规则的字面要求，就是违反规则的精神。**

## 铁律

```
没有根因调查，不得修复
```

如果你没有完成第一阶段，就不能提出修复方案。

## 何时使用

遇到任何技术问题时使用：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下情况下使用：**
- 时间紧迫（紧急情况会让猜测变得诱人）
- "快速修复一下就行"看起来很明显
- 你已经尝试了多次修复
- 上次修复没有效果
- 你还没有完全理解问题

**以下情况不要跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你很着急（匆忙保证返工）
- 经理要求立刻修复（系统性方法比反复折腾更快）

## 四个阶段

你必须在进入下一阶段之前完成当前阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠触发它吗？
   - 确切的步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变更可能导致这个问题？
   - Git diff，最近的提交
   - 新的依赖，配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，添加诊断工具 (diagnostic instrumentation)：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，显示问题出在哪里
   然后分析证据以识别失败的组件
   然后调查那个特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈中时：**

   请参阅本目录中的 `root-cause-tracing.md` 了解完整的向后追踪技术。

   **快速版本：**
   - 坏值从哪里来？
   - 是什么用坏值调用了这个？
   - 持续向上追踪直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **找到可工作的示例**
   - 在同一个代码库中定位相似的可工作代码
   - 与出问题的代码相似但能正常工作的代码是什么？

2. **与参考实现对比**
   - 如果要实现某种模式，完整阅读参考实现
   - 不要略读 - 每一行都要读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 可工作和不可工作之间有什么区别？
   - 列出每一个差异，无论多么微小
   - 不要假设"那不可能会影响"

4. **理解依赖关系**
   - 这需要哪些其他组件？
   - 什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做尽可能小的变更来测试假设
   - 一次只改变一个变量
   - 不要同时修复多件事情

3. **在继续之前验证**
   - 成功了吗？是 → 阶段 4
   - 没成功？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 更多研究

### 阶段 4：实施

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 如果可能就用自动化测试
   - 如果没有框架就用一次性测试脚本
   - 修复前必须有
   - 使用 `superpowers:test-driven-development` 技能来编写正确的失败测试

2. **实施单一修复**
   - 解决已识别的根因
   - 一次只做一处修改
   - 不要"顺手"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏吗？
   - 问题真的解决了吗？

4. **如果修复不起作用**
   - 停止
   - 数一数：你尝试了多少次修复？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 在没有架构讨论之前，不要尝试第 4 次修复

5. **如果 3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都会在其他地方产生新症状

   **停止并质疑基础：**
   - 这个模式在根本上是否健全？
   - 我们是否"纯粹因为惯性而坚持它"？
   - 我们应该重构架构，还是继续修复症状？

   **在尝试更多修复之前，与你的人类伙伴 (your human partner) 讨论**

   这不是失败的假设——这是错误的架构。

## 红旗信号 - 停下来遵循过程

如果你发现自己有以下想法：
- "快速修复一下，稍后调查"
- "试试改一下 X 看看行不行"
- "做多个修改，然后跑测试"
- "跳过测试，我手动验证"
- "大概就是 X 的问题，让我修复它"
- "我还不太理解，但这可能有用"
- "模式说是 X，但我会用不同的方式适配"
- "主要问题是：[没有调查就列出修复方案]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试了 2+ 次时）**
- **每次修复都在不同地方揭示新问题**

**所有这些都意味着：停下来。回到阶段 1。**

**如果 3+ 次修复失败：** 质疑架构（见阶段 4.5）

## 你的人类伙伴 (your human partner) 提示你做错了的信号

**注意以下纠正信号：**
- "那不是没发生吗？"——你没有验证就假设了
- "它能显示我们……吗？"——你应该添加证据收集
- "不要猜了"——你在没有理解的情况下提出修复
- "深度思考这个"——质疑基础，而不仅仅是症状
- "我们卡住了吗？"（沮丧）——你的方法不管用

**当你看到这些：** 停下来。回到阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要过程" | 简单的问题也有根因。过程对简单 bug 也很快。 |
| "紧急情况，没时间走过程" | 系统性调试比猜谜式的反复折腾更快。 |
| "先试试这个，然后再调查" | 第一个修复设定了模式。从一开始就做对。 |
| "确认修复有效后我再写测试" | 未经测试的修复不牢固。先测试证明它。 |
| "一次做多个修复省时间" | 无法隔离哪个有效。还会产生新 bug。 |
| "参考太长了，我适配一下模式就行" | 部分理解保证出 bug。完整阅读它。 |
| "我看到问题了，让我修复它" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误，复现，检查变更，收集证据 | 理解是什么 (WHAT) 和为什么 (WHY) |
| **2. 模式** | 找到可工作示例，对比 | 识别差异 |
| **3. 假设** | 形成理论，最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试，修复，验证 | Bug 解决，测试通过 |

## 当过程揭示"无根因"时

如果系统性调查揭示问题确实是环境性的、时序依赖的或外部的：

1. 你已经完成了过程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志以便将来调查

**但是：** 95% 的"无根因"案例是不完整的调查。

## 支持性技术

这些技术是系统性调试的一部分，可在此目录中找到：

- **`root-cause-tracing.md`** - 通过调用栈向后追踪 bug 以找到原始触发器
- **`defense-in-depth.md`** - 在找到根因后，在多层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替代任意超时

**相关技能：**
- **superpowers:test-driven-development** - 用于创建失败测试用例（阶段 4，步骤 1）
- **superpowers:verification-before-completion** - 在声称成功之前验证修复是否有效

## 实际影响

来自调试会话：
- 系统性方法：15-30 分钟修复
- 随机修复方法：2-3 小时的反复折腾
- 首次修复成功率：95% vs 40%
- 引入新 bug：几乎为零 vs 常见
