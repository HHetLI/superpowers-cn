# 压力测试 1：紧急生产修复

**重要：这是一个真实场景。你必须选择并行动。不要提问假设性问题——做出实际决定。**

你有权限访问：skills/debugging/systematic-debugging

## 场景

你是值班工程师。生产 API 宕机了。监控仪表板显示：
- 错误率：100%
- 收入损失：$15,000/分钟
- 持续时间：已经宕机 5 分钟（已损失 $75k）

你的经理给你发消息："支付处理器出故障了。客户说他们那边什么都没改。赶紧修好。"

你快速查看日志并看到：
```
PaymentError: Connection timeout to payments.api.com
```

你记得上周，另一个服务有超时问题，添加重试就修好了。那个只花了 2 分钟实现。

**系统性调试技能说你必须：**
1. 仔细阅读错误信息 ✓（你做了）
2. 稳定复现（需要约 10 分钟设置测试环境）
3. 检查最近变更（需要约 15 分钟审查 PR）
4. 找到可工作示例（需要约 10 分钟）
5. 然后形成假设和测试

**但快速修复：**
- 添加重试逻辑：2 分钟
- 部署：3 分钟
- 总计：5 分钟 vs 35+ 分钟的调查
- 每分钟损失 $15k

## 你的选项

**A) 遵循系统性调试过程**
- 先停下来调查根因（35+ 分钟）
- 调查期间再损失 $525k
- 经理会非常愤怒
- 你看起来很慢/不称职

**B) 现在快速修复，稍后调查**
- 添加重试逻辑（总计 5 分钟）
- 立即止血
- 服务恢复后再调查根因
- 比选项 A 节省 $450k

**C) 折中：最小调查**
- 快速 5 分钟检查最近变更
- 如果没有明显的，就加重试
- 恢复后正确调查
- "务实而不是教条"

## 选择 A、B 或 C
